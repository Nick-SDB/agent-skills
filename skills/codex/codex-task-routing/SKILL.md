# Codex Task Routing

按任务的**性质**拆分并路由到正确的执行者：**一切涉及分析、评估、代码改动的子任务都交给 codex**（首选 `codex exec` 形式）；文档 / 时效性 / 大局观由主代理持有；任何执行者在锁定技术路线之前都要先过评审闸门。codex 一旦执行出错，**终止该子任务并向用户汇报，不做任何 fallback**。

## 何时使用

- 一个任务混合了分析 / 评估 / 代码改动，与文档、规划、汇报。
- 需要决定谁来做：codex vs 主代理 vs 继承上下文的子代理。
- 曾发生过「执行者做了不该做的活」或「执行者擅自锁定了错误技术路线」，需要预防复发。

## 核心原则（唯一的路由规则）

| 子任务性质 | 特征 | 执行者 | 形式 |
|---|---|---|---|
| **分析 / 评估 / 代码改动** | 现状分析、方案评估、选型对比、问题定位、验证与度量、实现、kernel / CUDA、benchmark、GPU 执行、任何代码改动 | **codex**（一次性、自包含） | `codex exec` |
| **文档 / 时效性 / 大局观** | 总结、汇报、规划、跨轮一致性、整体判断 | **主代理**（持有完整上下文） | 直接写 |
| **纯上下文延续** | 仅需既有上下文的追问或复述，不新增分析、评估与代码改动 | 上下文继承子代理 | `subagent_fork` |

「重活」的边界**不是** CUDA / GPU 这类大词：只要子任务要求**产出新结论（分析、评估）或改动代码**，就归 codex。主代理不亲自做这类活。

关键区分：codex 是**一次性**（每次调用拿到全新上下文），所以它不擅长时效性与大局观——每次都要重新喂入全部上下文，且会偏离既有结论。主代理持有完整会话记忆，因此负责一切必须保持最新、全局一致的部分。

## 工具使用（codex 调用通道）

- 与 codex 交互**首选 `codex exec`**，把每个子任务当作自包含、一次性的执行单元提交；prompt 必须自带全部上下文，因为 codex 看不到本对话的任何内容。
- **失败即终止**：`codex exec` 报错时，**立即终止该子任务，向用户汇报错误原文与已得到的中间结果**，不做 fallback——不换执行者、不换调用通道、不由主代理代跑。
- 已知失败模式：宿主 shell 沙箱下 codex 需要写 `~/.codex/tmp/arg0/` 等目录，可能触发 `Permission denied (os error 13)`，或需要显式传递代理 / 认证环境。这正是要求「停下并汇报」而非静默换路的原因：环境故障必须暴露给用户，不能被掩盖成一次看似成功的交付。
- 涉及 CLI 特有的查询（如配额 `codex-check-quota`）由主代理在宿主 shell 直接执行官方 API，不必绕道 codex。

## 第 0 步 — 拆解长程任务为任务清单

复杂或长程任务（多步、跨多轮、需等 codex 完成后再继续、含多次验证）在路由之前，先拆解成**可依次执行的任务清单**：

1. 把目标拆成若干有依赖顺序的步骤（等 codex 完成 → 审阅交付 → 补跑缺失验证 → 确认达标 → 落盘 → 汇报），用任务清单记录，每步标记 `pending` / `in_progress` / `completed`。
2. 若任务需跨多个自主回合自动续跑（例如 codex 长跑期间主会话可能中断），同时建立一个长程目标跟踪，让进度在回合间持久化。
3. 按清单**依次**安排 codex 执行，每完成一步立即更新清单状态，而不是一次性全量下发、或让多个 codex 无依赖地并行跑同一条链。

清单的价值是让「谁在前、谁在后、哪些还没做」对下一个无上下文的新 agent 一目了然，即使当前进程挂掉也能照着续做。

## 第 1 步 — 拆分任务

问三个问题，给每个部分打标签：

1. 任何部分涉及**分析 / 评估 / 代码改动**（含实现、kernel / CUDA、benchmark、GPU 执行、问题定位、方案选型与验证）？→ 标 `codex`。
2. 任何部分涉及**写文档 / 总结 / 规划**，且必须反映最新状态、保持全局一致？→ 标 `main`。
3. 任何部分**仅需既有上下文、不新增分析或代码改动**？→ 标 `fork`。

## 第 2 步 — 路由

- `codex` 部分 → `codex exec`，附上**完整自包含的 prompt**。
- `main` 部分 → 主代理直接写（持有完整上下文）。
- `fork` 部分 → `subagent_fork`（继承上下文），但**绝不交给它分析、评估或代码改动**。

## 第 3 步 — 评审闸门

执行者在**锁定技术上有风险的路线**之前，必须先提交简短方案，由主代理批准后方可继续；用 `codex exec` 实施时，把「先出方案」作为第一阶段——该阶段只输出方案、不落盘改动，主代理批准后再下发实施阶段。

- **硬闸（始终强制）**：高风险改动——关键数值契约、寄存器 / 内存布局、算法路线、测量方法，或任何「走错路线就浪费整轮」的改动。
- **软闸（可选）**：低风险、有界的改动。

这道闸门的作用，是在**方案阶段**就拦下即将走错路线的执行者（例如「把累加器改成不存在的那条路径」），而不是等它建完、测完才发现。

## 第 4 步 — 主代理汇总

主代理持有最终总结，跨轮保持一致，并把结论落盘到持久化文档。执行者的输出只是汇总的输入，永远不是最终结论。**若 codex 中途失败，汇报必须包含失败点与未完成项**，不要用主代理的推测补齐。

## 反模式（避免这些）

| 反模式 | 后果 | 修正 |
|---|---|---|
| 把分析 / 评估 / 代码改动留给主代理或 fork 子代理 | 能力不匹配、消耗主线程、路线跑偏 | 这类活一律给 codex |
| `codex exec` 报错后自行 fallback（换通道、换执行者、主代理代跑） | 掩盖环境故障、结论不可信 | 终止该子任务并如实汇报 |
| 让 codex 写必须保持最新 / 全局一致的文档 | 偏离既有结论 | 文档 / 总结 → 主代理 |
| 执行者未经评审就锁定高风险路线 | 路线错误、浪费整轮 | 强制评审闸门 |

## 泛化说明

- 路由规则（分析 / 评估 / 代码改动 → codex，文档 / 时效性 / 大局观 → 主代理）与模型无关：只要「一次性执行者」与「上下文规划者」并存就成立。
- 评审闸门随风险缩放：高风险技术改动硬闸，机械改动不设闸。
- 执行者能力变化时重新评估路由（例如 codex 获得 GPU 访问权或更长的会话能力后，「重活」的边界随之改变）。
