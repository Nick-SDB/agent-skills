# First Principles Thinking (第一性原理思维)

把复杂问题分解为不可再分的基本事实,再基于这些事实向上推理,避免掉进「靠类比推理」的陷阱。

## 何时使用本 skill

- 评估某架构 / 设计是否真正最优
- 质疑可能并不契合当前情境的「最佳实践」
- 当常规方案显得不够用时,寻求突破
- 做出会产生长期影响的基础性决策
- 挑战遗留系统中的既有假设
- 不做「样板化照搬」地设计新系统

先做一次成本判断:第一性原理分析有成本,应优先用于重要、长期、基础性的决策;**琐碎 / 低风险 / 机械决定**不必走完整流程,用文末的 checklist 简做即可。不要对每个决定都无限投入。

## 核心流程

### 阶段 1:识别问题的本质
剥离实现细节,找到核心问题:
1. **把问题说清楚** - 到底要解决什么?
2. **把症状与原因分开** - 这是真问题还是表象?
3. **定义成功标准** - 一个完美方案要做到什么可衡量的结果?

关键问题:
- 这里真正要完成的「工作」(job to be done)是什么?
- 如果这套系统不存在,用户实际上需要什么?
- 哪些结果真正重要,与怎么实现无关?

### 阶段 2:挑战所有假设
找出并质疑每一个假设:
1. **列出显式假设** - 我们默认接受了什么?
2. **暴露隐式假设** - 我们在不假思索地遵循什么惯例?
3. **逐个检验假设** - 这真是约束,还是只是「一直这么做」?

假设类别:

| 类别 | 要问的问题 |
|---|---|
| 技术 | 必须用这个技术 / 模式吗? |
| 业务 | 这个需求真的是固定的吗? |
| 资源 | 这些约束是真实存在还是臆想的? |
| 历史 | 这个决定当初是为什么做的? |

可能是错误假设的红旗:
- 「我们一直这么做」
- 「行业标准就是这样」
- 「大家都用 X 做这个」
- 「这简单到不可能有用」

### 阶段 3:确立基本事实(Ground Truths)
找出不可再分的、确凿的事实:
1. **物理 / 数学约束** - 什么不能被违背?
2. **业务不变量** - 什么必须对业务始终成立?
3. **用户需求** - 用户真正需要什么?

基本事实检验:
- 还能不能再分解?
- 这是可证明为真,还是只是普遍相信?
- 违背它是否必然导致失败?

### 阶段 4:从基本事实向上推理
基于基本事实构建方案:
1. **从最小开始** - 满足基本事实的最简方案是什么?
2. **只加必要的东西** - 每次增加都必须能自证其必要性。
3. **挑战每一层** - 这一层复杂度配得上它吗?

```
Ground Truth → Minimal Solution → Justified Additions → Final Design
     ↑              ↑                    ↑
  (proven)     (sufficient)        (each defended)
```

### 阶段 5:验证推理
确保方案站得住脚:
1. **回溯到基本事实** - 每个设计决定都能追溯到某个根本需求吗?
2. **找出薄弱环节** - 推理在哪里依赖假设?
3. **压力测试** - 什么会破坏这个方案?

## 输出格式

应用第一性原理时,整合为如下结构:

```markdown
## First Principles Analysis: [主题]

### 1. Problem Essence
**Core problem:** [一句话]
**Success criteria:** [可衡量的结果]

### 2. Assumptions Challenged
| Assumption | Challenge | Verdict |
|------------|-----------|---------|
| [假设] | [为什么质疑它] | [保留/丢弃/修改] |

### 3. Ground Truths
- [不可再分的事实 1]
- [不可再分的事实 2]
- [不可再分的事实 3]

### 4. Reasoning Chain
Ground Truth → [步骤 1] → [步骤 2] → Solution

### 5. Conclusion
**Recommended approach:** [描述]
**Key insight:** [第一性原理分析揭示了什么]
**Trade-offs acknowledged:** [我们接受了什么]
```

## 常见模式

### 模式:复杂度陷阱
- 症状:方案比问题本身还要复杂
- 检查:移除一个组件,系统是否仍解决核心问题?是 → 该组件不必要;重复直到移除会破坏核心功能。

### 模式:类比陷阱
- 症状:「X 公司这么做,所以我们也可以」
- 检查:X 公司当时解决的是什么问题?我们的问题在所有相关维度上是否一致?他们有哪些我们没有的约束(反之亦然)?

### 模式:遗留陷阱
- 症状:维持与已经不再服务我们的决策的兼容
- 检查:这个决定当初的原因是什么?那些条件现在是否还存在?改变的真实成本 vs 维持的成本?

## 与其他思考方式结合

| 工具 | 何时结合 | 怎么结合 |
|---|---|---|
| 权衡分析 | 确立基本事实后 | 针对根本约束评估各选项 |
| 5-Whys | 假设浮现时 | 深挖根本原因 |
| Pre-mortem | 定稿前 | 压力测试推理链 |
| 假设检验 | 基本事实不确定时 | 实证验证假设 |

## 边界

**会做:**
- 系统性挑战假设
- 从第一性原理识别基本事实
- 基于基本事实构建推理链
- 揭示常识何时不适用

**不会做:**
- 把所有现有方案都判为错误
- 对每个决策无限投入(应保留给重要选择)
- 为理论纯粹而忽略实际约束
- 保证「最佳」方案(它揭示的是更正确的推理,不是完美答案)
